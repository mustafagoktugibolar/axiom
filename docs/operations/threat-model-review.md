# Threat model review (plan item 12.1)

Reviewed against `axiom-engineering-governance-plane/docs/02-architecture/security-threat-model.md` at commit 4f97fd6 plus the changes of this branch. Severity is the residual risk after the control found: High, Medium, Low, Info. "Fixed" means changed in this branch with a test; everything else is a finding only, with no enforcement semantics changed.

Note: `docs/implementation-dependencies.md` named in the brief does not exist in the repository.

## Per-threat review

| Threat | Control found in code | Gaps | Severity |
|---|---|---|---|
| T1 Agent claims pass without calling Axiom | PR stage is a hard gate on immutable SHAs (`DiffEvaluationService.ExecutePullRequestAsync`, `RequestLimits.CommitSha`); IDs and receipts are server-issued (`EvaluationIdentity`, `ReceiptFactory`); status published to SCM (`PullRequestStatusReporter`). | Branch protection is configuration outside the repo; nothing verifies that the Axiom check is marked required. SCM status publish failures are only counted (`axiom.scm.status_failures`). | Low |
| T2 Prompt injection in repo content | Verdicts come from deterministic rules; semantic output is advisory and never BLOCK (`SemanticAnalyzer`); per-call random delimiter and strict typed output (`SemanticPrompt.cs`, `AnthropicSemanticProvider`); findings must cite packet records/files. | Free-text model explanation is sanitised and truncated but shown to reviewers. | Low |
| T3 Unauthorized decision acceptance | Git remains authority; roles in `Authorizer` (`Security.cs`); reviewer cannot be the author (`ReviewService.EnsureIndependent`); routing to owner teams (`EnsureEntitled`); subject comes from token. | Role `Approver` may review anything without team routing (by design). Scope `axiom.exception.request` or `axiom.evaluate` both map to the full `Contributor` role (also grants ProposeDecision, RequestException, Evaluate): scope-to-role mapping is coarser than the scope names suggest (AxiomAuth.ScopeRoles). | Low (R-6) |
| T4 Exception abuse | Scoped targets, expiry, max 180 days, tracking issue, requester cannot decide, routed approvers, non-exemptable validation via `GovernanceSetValidator` (`ExceptionRequestService`). Approval waives nothing until merged in Git. | `axiom.exception.usage` is emitted, but an "exception expiring with active usage" alert has no metric (needs expiry timestamps). A coarse high-usage alert exists in `deploy/observability/axiom-alerts.yaml`. | Low |
| T5 Custom policy runner | Built-in rules run in process with hard input bounds (`PolicyLimits`). `Axiom.PolicyRunner` is an empty stub (`return 0`); no custom executable rules exist, and an architecture test keeps it from reaching state. | When custom rules are implemented, sandboxing (rootless, no network, limits, signed artifacts) is entirely unimplemented. No Kubernetes NetworkPolicy ships in `deploy/`. | Info now, High when custom rules land (R-7) |
| T6 Sensitive code to external LLM | Off by default; `semanticExternalAllowed:false` yields `ProhibitedByScope` before any call; bounded packet with added lines only; secret scrubbing (`EvidencePacketBuilder`); Heuristic local provider; redirects disabled for Anthropic client. | Scrubbing is regex-based best effort. The task text is sent (scrubbed, truncated). No per-organization provider policy, only a per-record flag. Defect fixed: see R-1. | Medium |
| T7 Cross-tenant leakage | Org taken from the token, never the body (`Authorizer.Demand`, `AxiomAuth.ToPrincipal`); every table keyed by (OrganizationId, ...) and every query reviewed filters by `OrganizationId` (`EfEvaluationStore`, `EfReviewStore`, `EfExceptionRequestStore`, `GovernanceReaders`); rate limit partitioned by org and subject. | Isolation relies on every query remembering the filter: no EF global query filter or Postgres row-level security as defence in depth. No vector search exists, so no global vector search risk. No tenant-scoped encryption. | Medium (R-5) |
| T8 Receipt tampering | Canonical payload hash, per-org hash chain with advisory-lock serialisation (`ReceiptFactory`, `EfEvaluationStore.AppendAsync`); `Verified` recomputed on every read; `VerifyChainAsync`. | Fixed R-2 (below). Remaining: R-3, R-4. | Medium |

## Findings

| ID | Finding | Severity | Status |
|---|---|---|---|
| R-1 | `SemanticAnalyzer` trusted `Confidence` from any `ISemanticProvider`. NaN passed the `< MinConfidence` check, became a stored finding, and made JSON serialization of the evaluation fail at receipt append (a provider could turn an evaluation into a 503). Infinity or >1 would be treated as top confidence. Only the Anthropic parser validated the range. | Medium | Fixed in `SemanticAnalyzer.Validate`: non-finite or out-of-[0,1] findings are dropped. Tests: `DegradationTests.Garbage_that_parses_but_is_out_of_contract...` |
| R-2 | `ReceiptFactory.Verify` checked only payload digest and chain link. The columns users read (`Verdict`, `EvaluationId`, `Stage`, `Repository`, `CommitSha`, `SnapshotId`, `IssuedAt`, `Id`) were not bound to the payload, so someone with database write access could change a stored `BLOCK` to `ALLOW` and `Verified` stayed true. | High | Fixed: `Verify` now checks `Id == rc_ + digest[..24]` and that each column equals the signed payload. Tests: `ReceiptReplayTests.Altering_any_stored_receipt_field...` (13 fields). |
| R-3 | Receipt hash includes the issue time, so replay is hash-identical only with a fixed clock. The evaluation ID is stable across the validity epoch. Evaluations are cached by ID, so the first receipt is returned. This is by design, documented by test. | Info | Not a defect |
| R-4 | The evaluation document (`evaluations.document`) is not checked against its receipt on read, and nothing anchors the chain head. Modifying the document is undetected by `VerifyChainAsync`; deleting the newest receipts leaves a valid prefix. Also no database-level append-only enforcement (no triggers or revoked UPDATE/DELETE). `ReceiptFactory.Matches(evaluation, receipt)` was added so callers can verify the document; it is not wired into read paths (would change API behaviour). | Medium | Open. Recommend: verify document vs receipt in `EfEvaluationStore.FindAsync`, publish chain head to external WORM/object storage, revoke UPDATE/DELETE for the app role. |
| R-5 | No defence in depth for tenant isolation (see T7). | Medium | Open |
| R-6 | OAuth scope to role mapping coarser than scope names (see T3). | Low | Open |
| R-7 | No NetworkPolicy in `deploy/`; workers container lacks `readOnlyRootFilesystem`; `/openapi` and `/v1/auth/config` are anonymous (acceptable but expose surface). | Low | Open |
| R-8 | Receipt payload omits requiredChecks, affected dependencies, resolved scope, trace and the actor display name; it covers the verdict-determining inputs (findings, applied records/exceptions, policy runs, snapshot, catalog version). | Info | Accept |
| R-9 | Degradation behaviour (R24): semantic outage gives `Degraded` coverage with deterministic verdict intact; SCM, snapshot, catalog or database failures abort with a retryable `Unavailable` error and store nothing (fail closed, never ALLOW). A catalog outage fails the evaluation rather than degrading, which is stricter than R24 requires. No vector retrieval exists in the evaluation path. | Info | Verified by `Chaos/DegradationTests` |
| R-10 | Observability gaps: the instruments `axiom.ingestion.lag` and `axiom.policy.violations` are defined but never recorded; no HTTP server metrics are exported (ASP.NET Core metrics instrumentation is not added), so availability SLO 99.9% and governance-search p95 cannot be alerted on; no metric for "hard rule evaluation unavailable". The dashboard and alerts use only the metrics that exist; the lag alert stays silent until the synchronizer records it. | Medium | Open |
